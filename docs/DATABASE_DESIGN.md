# Database Design

## Scope and database role

Campus Ride Match uses SQLite as the system of record. Flask routes validate input and enforce authorization, but durable identities, relationships, lifecycle values, uniqueness, seat bounds, and referential integrity are protected by `schema.sql`. The application uses parameterized raw SQL so the course-relevant joins, overlap predicates, aggregations, and transactions remain visible.

## Tables

| Table | Purpose | Primary and foreign keys |
|---|---|---|
| `users` | Account, login identity, display name, and contact details. | PK `id`; unique `username` and `email`. |
| `location_areas` | Controlled, reusable fixed areas used for exact search. Specific meeting text remains on a trip. | PK `id`; unique `name`. |
| `trips` | A publisher's route, date, acceptable time range, capacity, remaining seats, and lifecycle. | PK `id`; FK `publisher_id -> users`; FKs `origin_area_id` and `destination_area_id -> location_areas`. |
| `match_requests` | Every attempt by a user to join a trip, including historical rejected/cancelled attempts. | PK `id`; FKs `trip_id -> trips`, `requester_id -> users`. |
| `trip_participants` | Accepted-participant history and its active/ended state. This is the associative entity for the user–trip M:N relationship. | PK `id`; FKs `trip_id -> trips`, `user_id -> users`, unique FK `request_id -> match_requests`. |
| `notifications` | Per-user in-app lifecycle events. | PK `id`; FK `user_id -> users`; optional FKs to `trips` and `match_requests`. |
| `reviews` | A rating/comment from one actual trip member to another after completion. | PK `id`; FKs `trip_id`, `reviewer_id`, and `reviewee_id`. |

All foreign keys use `ON DELETE RESTRICT` because course records are historical data; lifecycle changes use status values rather than destructive deletion. Every application connection enables `PRAGMA foreign_keys = ON`.

## Relationships

- One user publishes zero or many trips; every trip has exactly one publisher.
- A trip has one origin and one destination fixed area; each area can be used by many trips in either role.
- One user submits many match requests, and one trip receives many requests.
- Users join many trips and trips have many users through `trip_participants`.
- An accepted request produces at most one participant row because `request_id` is unique.
- A trip has many reviews. Users appear separately as reviewer and reviewee.

See [ER_DIAGRAM.md](ER_DIAGRAM.md) for the implemented cardinalities and attributes.

## Integrity constraints

The schema uses the following database-level rules:

- Integer primary keys identify every row.
- Required relationship and business fields use `NOT NULL`.
- Usernames, emails, and area names are case-insensitively unique.
- Trip status is limited to `Open`, `Full`, `Completed`, or `Cancelled`.
- Request status is limited to `Pending`, `Accepted`, `Rejected`, or `Cancelled`.
- Participant status is limited to `Active`, `Left`, `Removed`, or `TripCancelled`.
- Notification event type is limited to the five events generated by the application.
- Rating values must be within 1 through 5; reviewers cannot review themselves. Application forms parse integer ratings. The schema uses ordinary SQLite affinity, not STRICT typing.
- `(trip_id, reviewer_id, reviewee_id)` is unique, preventing duplicate reviews for the same pair and trip.
- Time text must have `HH:MM` form, hours must be 00–23, and `start_time <= end_time`.
- Capacities and publisher party sizes are 1–20. Remaining seats must be between zero and capacity.
- A `Full` trip must have zero remaining seats, and an `Open` trip must have at least one.
- An active participant must have no `ended_at`; every ended participation must have one.
- Partial unique index `uq_requests_active` allows historical retries but only one `Pending`/`Accepted` request per user and trip.
- Partial unique index `uq_participants_active` allows preserved history but only one active participation per user and trip.

Cross-row or authorization rules—such as “the requester is not the publisher” and “reviewers actually took this completed trip”—are checked in Flask because SQLite `CHECK` constraints cannot query another table. The tests cover these rules. The `audit-db` command additionally detects foreign-key failures, seat-count mismatches, accepted requests without active participants, missing participation end timestamps, and status/seat disagreement.

## Functional dependencies and normalization

Important dependencies are:

- `users.id -> username, password_hash, display_name, email, phone, created_at`; `username` and `email` are alternate keys.
- `location_areas.id -> name, is_active`; `name` is an alternate key.
- `trips.id ->` every trip attribute.
- `match_requests.id -> trip_id, requester_id, status, created_at, updated_at`.
- `trip_participants.id -> trip_id, user_id, request_id, status, joined_at, ended_at`; `request_id` is also a candidate key.
- `notifications.id ->` every notification attribute.
- `reviews.id ->` every review attribute; `(trip_id, reviewer_id, reviewee_id)` is an alternate key.

**First normal form (1NF).** Every column contains one scalar value. Repeating participants, requests, and reviews are rows in separate relations, not lists stored in a trip.

**Second normal form (2NF).** Tables use single-column primary keys, and non-key attributes depend on the entire key. The alternate composite review key also determines rating, comment, and creation time; there is no dependency on only part of that key.

**Third normal form (3NF).** User/contact facts are stored only in `users`; fixed-area names only in `location_areas`; request facts only in `match_requests`; participation facts only in `trip_participants`. Queries obtain related names through joins rather than copying them into trips or requests. No non-key descriptive attribute determines another non-key descriptive attribute within these relations.

`available_seats` is deliberate, controlled denormalization: it can be derived from `seat_capacity - active participant count`. It is retained to make availability filtering and the central acceptance transaction explicit. Transactions maintain it, and `audit-db` checks it against active participants. The benefit and consistency cost are therefore visible rather than hidden.

## Meaningful queries

The application demonstrates:

- Multi-condition trip search across trips, users, and two area aliases.
- Inclusive interval overlap: `trip.start_time <= search_end AND trip.end_time >= search_start`.
- `EXISTS` conflict detection across published and joined trips.
- My Trips joins across trips, users, areas, requests, and participants.
- Incoming request retrieval with requester identity and route data.
- `AVG` and `COUNT` review summaries.
- Insights aggregations using `GROUP BY` for lifecycle counts, origins, destinations, and routes.
- `NOT EXISTS` filtering in the course sample query set.

Runnable examples are in [`sql/sample_queries.sql`](../sql/sample_queries.sql).

## Transactions and consistency

Accepting a request uses `BEGIN IMMEDIATE`, which obtains a write reservation before rechecking mutable state. Within one transaction the route:

1. Reloads the request and trip.
2. Requires the request to remain `Pending` and the trip to remain `Open` with a seat.
3. Rechecks expiry and the requester's schedule using an `EXISTS` overlap query.
4. Atomically decrements `available_seats` and changes the trip to `Full` when the last seat is taken.
5. Changes the request to `Accepted`.
6. Inserts the `trip_participants` row.
7. Inserts the notification and commits.

Any error or failed recheck rolls the transaction back. This prevents accepted-without-participant, participant-without-seat-decrement, negative-seat, and incorrect-`Open` states.

Withdrawal/removal also uses `BEGIN IMMEDIATE`: it ends the active participant row, restores exactly one seat, returns `Full` to `Open`, cancels the associated accepted request, and optionally creates a notification. Trip cancellation atomically closes active requests and participants and restores capacity. Trip completion atomically marks the trip completed and closes pending requests.

## Indexing strategy

| Index | Query supported | Reason for column order |
|---|---|---|
| `idx_trips_search(trip_date, origin_area_id, destination_area_id, status, start_time, end_time)` | Exact date/area search plus lifecycle and overlap filtering. | Equality predicates come first; range times follow them. |
| `idx_trips_publisher(publisher_id, status)` | Published trips, incoming-request ownership, and active schedule conflicts. | Publisher is the leading equality lookup; status narrows active rows. |
| `idx_requests_trip_status(trip_id, status)` | Requests for a trip and request lifecycle updates. | Trip ownership is selected first, then status. |
| `idx_requests_user_status(requester_id, status)` | A user's request history and active-request checks. | Requester is the leading lookup. |
| `idx_participants_trip_status(trip_id, status)` | Participant lists, seat audits, contact access, and review eligibility. | Trip first, active/historical state second. |
| `idx_participants_user_status(user_id, status)` | Joined trips and schedule conflict `EXISTS`. | User first, then active state. |
| `idx_notifications_user_unread(user_id, read_at, created_at DESC)` | Unread badge and notification list. | User and unread state filter before recency ordering. |
| `idx_reviews_reviewee(reviewee_id)` | Profile average rating and review count. | All rating aggregates filter by reviewee. |

SQLite automatically indexes unique keys. The two partial unique indexes both enforce lifecycle integrity and accelerate active-state lookups. Indexes are not added to low-selectivity columns alone; for example, `status` is useful as a suffix but not a standalone index for this small status domain.

## Audit scope clarification

The current audit reports 13 violation counts, including request/participant identity and lifecycle mismatches. It detects inconsistency rather than repairing it, and is not an exhaustive calendar or scheduling validator. Date-shape checks are distinct from application calendar validation. Participant user/trip identifiers repeat facts derivable through request_id, and notification trip references can repeat facts derivable through request_id; these cross-table redundancies require application validation even with the entity-level normalization described above.
